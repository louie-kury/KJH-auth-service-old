# 일반 회원가입 API — 실행 계획서

- 상태: 실행 중. 작성일: 2026-11-24. 사용자와 가입 범위·증명 처리 방식을 합의하고 이슈 및 브랜치를 생성했다.
- 대상: `louie-kury/KJH-auth-service`. 조사 시 `feat/5-signup-email-verification`은 원격과 일치하고 미커밋 변경이 없었다.
- 이슈: https://github.com/louie-kury/KJH-auth-service/issues/7. 브랜치 `feat/7-signup-api`. 사용자 요청에 따라 중복 확인 구현은 커밋됐고 일반 가입 구현을 진행한다. 추가 커밋·푸시·PR은 별도 요청 범위다.

## 목적과 범위

`POST /api/auth/signup`에서 이메일 인증 증명을 검증하고 일반 계정·로그인 정보와 프로필을 생성한다. 증명을 한 번 소비하고 계정 중복을 DB 제약으로 방지한다. 소비 후 실패하면 재인증이 필요하다. 기존 인증번호 발송·확인을 유지한다. 로그인, 소셜 가입, 계정 복구, 프론트엔드는 제외한다.

## 조사 근거와 제약

- 공통 PRD `ACC-01`, 6.10, D11·D18, Q06·Q22: 가입 전 이메일 인증, 이메일 유일성, 프로필 완료 요구. 약관별 필수 여부와 동의 기록은 미정이다.
- 공통 `docs/erd/svc_identity.md`: `account`의 이메일과 UUID는 유일하며 약관 동의 등 필수 항목이 있다. `login_credential`은 계정 FK, 계정 ID·로그인 ID 유일 제약이 있다. `user_profile`은 계정 FK와 닉네임 유일 제약을 두지만, PRD의 MongoDB 프로필과 저장 위치가 충돌한다. 실제 DB 적용 여부를 별도 확인한다.
- 공통 `docs/api/README.md`, `docs/api/auth.md` 가입 절: 기존 멱등 계약은 사용자 결정으로 변경됐다. `201`, `Location: /api/members/me`, 이메일과 SIGNUP 목적에 묶인 증명은 유지한다. 공통 문서 동기화는 별도 범위다.
- 서비스 README, `account` 저장 코드와 `emailverification`의 Redis 저장 코드: #3의 계정·자격증명 저장 및 Argon2id, #5의 증명 발급은 존재한다. 가입 API와 증명 소비는 후속 작업이다.
- 서비스 기존 계획 `2026-11-23-auth-mysql-account-login.md`와 공통 이메일 인증 계획: 기존 결정은 개인정보를 현재 ERD 컬럼 형식으로 저장하고 비밀번호는 15~128 Unicode 코드 포인트이며 문자 종류를 강제하지 않는다. 이는 공통 PRD의 이전 암호화·비밀번호 정책과 다르다. 이메일은 ASCII이며 전체 대소문자를 구분하지 않는다.
- 공통 백엔드 컨벤션의 계층·DTO·영속성·트랜잭션·오류·테스트 절을 따른다. 화면 및 프론트엔드 규칙은 범위 밖이다.

## 제안하는 동작과 선택

1. 입력을 검증하고 Redis에서 이메일·목적·만료를 확인해 증명을 원자적으로 소비한다.
2. 계정·자격증명·프로필을 MySQL 한 트랜잭션으로 저장하고 DB 유일 제약으로 중복을 처리한다.
3. 증명 소비 후 실패하면 재인증한다. 응답 유실 후 재인증·재요청 시 중복 오류가 발생할 수 있으며 이전 성공 결과는 재응답하지 않는다.

## 구현 전 검토할 사항

- 이번 가입은 ERD와 실제 MySQL `user_profile`을 기준으로 한다. MongoDB 프로필 저장 여부는 회원가입 구현 완료 후 검토한다.
- 사용자 결정: 약관 항목이 정해지기 전까지 가입 시 전체 동의한 것으로 처리하고 MySQL의 필수 동의값을 설정한다. 실제 항목·필수 여부·버전·동의 기록은 추후 결정한다.
- 사용자가 결정한 Redis 증명 원자 소비 후 MySQL 저장 방식을 아래에 반영한다.
- #3의 개인정보·비밀번호 정책과 공통 문서의 이전 정책 차이, 이메일 비교 기준과 DB 컬레이션 차이를 확인한다. 기존 사용자 결정을 바꾼 것으로 가정하지 않는다.
- 성별 코드, 상세 주소, 로그인 ID 비교 및 닉네임 제한을 제품 정책과 실제 DB 제약에 대조한다.

5. 공통 PRD·API·ERD는 기존 사용자 지시대로 회원가입 구현 완료 후 실제 결과와 대조해 한 번에 정리한다.

- 같은 증명의 동시 소비, 중복 가입 및 Redis 소비·MySQL 커밋·응답 전후 장애와 재인증을 검증한다.

- 인증·개인정보·외부 연동 경계의 독립 코드·보안 리뷰를 수행한다. 실패나 필수 검증 불가를 성공으로 처리하지 않는다.

계획과 이슈 범위를 사용자와 검토하고 #7 브랜치를 생성했다. 중복 확인은 구현·격리 DB/실제 서버 검증 후 커밋됐다. 일반 가입 구현은 별도 검증이 필요하다.

## 추가 요청: 가입 전 중복 확인 API

- 로그인 ID와 닉네임의 사용 가능 여부를 각각 조회하는 공개 API 두 개를 회원가입 범위에 추가한다. 경로·입력·응답은 아래 결정에 따르고 요청 제한은 별도 정책을 확인한다.
- 사전 확인은 값을 예약하지 않는다. 확인 후 동시 가입이 가능하므로 가입 저장 시 DB 유일 제약으로 다시 검증하고 중복을 충돌로 반환한다.
- 로그인 ID는 기존 MySQL `login_credential.login_id` 제약 및 실제 비교 규칙을 따른다. 닉네임은 MySQL `user_profile.nickname`의 유일 제약과 비교 규칙을 사용한다.
- 사용 가능·중복·잘못된 입력, 대소문자 등 비교 기준, 확인 직후 다른 요청이 선점하는 경합을 테스트한다. 실제 MySQL 유일 제약은 아래 읽기 전용 조사 결과를 따른다.

## 1단계 조사 결과 — 2026-11-24

- 설정된 실제 MySQL의 `information_schema`를 읽기 전용으로 조회했다. `login_credential.login_id`는 `VARCHAR(100) NOT NULL`, `uk_login_id` 단일 컬럼 UNIQUE다. `user_profile.nickname`은 `VARCHAR(50) NOT NULL`, `uk_profile_nickname` 단일 컬럼 UNIQUE다.
- 두 컬럼의 컬레이션은 `utf8mb4_0900_ai_ci`로 대소문자와 악센트를 구분하지 않는다. 정확한 입력 정규화·공백·문자 길이 규칙과 가입 API의 비교 방식은 별도 확정한다. 데이터 조회·변경은 하지 않았다.
- PRD ACC-01은 일반 회원 프로필의 MongoDB 저장을 확정했지만 실제 MySQL과 ERD에 닉네임 UNIQUE를 가진 `user_profile`이 존재한다. 사용자는 이번 구현에서 ERD 기준 MySQL을 우선하고 MongoDB 프로필 저장은 가입 구현 완료 후 검토하기로 했다. 실제 MongoDB 인덱스는 조사하지 않았다.
- PRD는 약관 내용을 MongoDB, 계정 동의 여부를 MySQL에 저장하도록 정하지만 약관별 필수 여부, 버전과 동의 기록 방식은 미정이다. 사용자 지시에 따라 이번 가입에서는 동의한 것으로 임시 처리하며 실제 약관·기록 정책은 나중에 정한다.
- 프로필은 이번 구현에서 ERD 기준 MySQL을 사용한다는 사용자 결정을 따른다. 약관은 이번 가입에서 동의 상태로 임시 처리하고 세부 정책은 추후 결정한다. 공통 문서 동기화는 가입 구현 후로 보류한다.


## 약관 임시 처리 결정 — 2026-11-24

- 사용자는 실제 약관과 필수 항목이 정해지지 않아 이번 가입에서 모두 동의한 것으로 처리하도록 지시했다. 가입 요청에 개별 약관 선택을 추가하지 않고 기존 MySQL 필수 동의 상태를 설정한다.
- 실제 약관 내용·필수 여부·버전·개별 동의 기록은 구현 이후 별도 결정한다. 이 임시 상태는 실제 약관을 보여주고 동의를 받은 증거가 아니다.


## 중복 확인 API 경로 결정

- `GET /api/auth/login-ids/availability?loginId=...`: 로그인 아이디 사용 가능 여부.
- `GET /api/auth/nicknames/availability?nickname=...`: 닉네임 사용 가능 여부.
- 성공 응답은 공통 형식의 `{"data":{"available":true}}`이며 사용 중이면 `false`다. 유효하지 않은 입력은 검증 오류로 처리한다. 조회는 예약이 아니므로 가입 시 유일 제약을 다시 검사한다.

## 일반 가입의 증명 처리 — 2026-11-25

- 사용자 결정: 가입 `Idempotency-Key`와 `signup_idempotency` 테이블을 제거한다. Redis에서 증명의 이메일·SIGNUP 목적·만료를 검증하고 원자적으로 소비한 뒤 MySQL에 저장한다.
- `account`의 uuid·email, `login_credential`의 account_id·login_id, `user_profile`의 account_id·nickname은 각각 유일하다. 계정·자격증명·프로필은 한 MySQL 트랜잭션으로 저장한다. 인증 증명과 MySQL 저장은 하나의 트랜잭션이 아니다.
- 소비 후 DB 저장 실패 등으로 가입이 완료되지 않으면 다시 이메일 인증을 받아야 한다. 성공 응답이 유실된 경우 재인증 후 재요청하면 중복 오류가 발생할 수 있다. 기존 성공 결과 재응답은 보장하지 않는다.
- 유효성 오류, 증명 만료·재사용·동시 소비, DB 중복·롤백, Redis 장애 및 소비 후 저장 실패와 응답 유실을 검증한다. 단위·웹 검증과 격리 MySQL·Redis 및 실제 서버 검증은 구분해 보고한다. 공유 DB는 변경하지 않는다.
- 사용자 결정: 성별 `MALE`·`FEMALE`, 신규 계정 `ACTIVE`, 프로필 유형 `CAREGIVER`. 약관은 임시 동의 상태로 저장하며 세부 정책은 추후 결정한다.

## 가입 코드값 확정
