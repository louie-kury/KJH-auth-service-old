- 상태: 실행 중. 작성일: 2026-11-24. 사용자와 가입 범위·증명 처리 방식을 합의하고 이슈 및 브랜치를 생성했다.
- 대상: `louie-kury/KJH-auth-service`. 조사 시 `feat/5-signup-email-verification`은 원격과 일치하고 미커밋 변경이 없었다.
- 이슈: https://github.com/louie-kury/KJH-auth-service/issues/7. 브랜치 `feat/7-signup-api`. 사용자 요청에 따라 중복 확인 구현은 커밋됐고 일반 가입 구현을 진행한다. 추가 커밋·푸시·PR은 별도 요청 범위다.

## 목적과 범위

`POST /api/auth/signup`에서 이메일 인증 증명을 검증하고 일반 계정·로그인 정보와 프로필을 생성한다. 중복 요청과 저장 중 실패에도 중복 계정을 만들지 않고 재시도할 수 있어야 한다. 기존 인증번호 발송·확인을 유지한다. 로그인, 소셜 가입, 계정 복구, 프론트엔드는 제외한다.

## 조사 근거와 제약

- 공통 PRD `ACC-01`, 6.10, D11·D18, Q06·Q22: 가입 전 이메일 인증, 이메일 유일성, 프로필 완료 요구. 약관별 필수 여부와 동의 기록은 미정이다.
- 공통 `docs/erd/svc_identity.md`: `account`의 이메일과 UUID는 유일하며 약관 동의 등 필수 항목이 있다. `login_credential`은 계정 FK, 계정 ID·로그인 ID 유일 제약이 있다. `user_profile`은 계정 FK와 닉네임 유일 제약을 두지만, PRD의 MongoDB 프로필과 저장 위치가 충돌한다. 실제 DB 적용 여부를 별도 확인한다.
- 공통 `docs/api/README.md`, `docs/api/auth.md` 가입 절: `Idempotency-Key`, `201`과 `Location: /api/members/me`, 이메일과 SIGNUP 목적에 묶인 증명, 같은 키·입력의 결과 반환 또는 복구, 다른 입력의 409, 진행 중 503을 정의한다. 인증 API 파일은 미커밋 초안이다.
- 서비스 README, `account` 저장 코드와 `emailverification`의 Redis 저장 코드: #3의 계정·자격증명 저장 및 Argon2id, #5의 증명 발급은 존재한다. 가입 API와 증명 소비는 후속 작업이다.
- 서비스 기존 계획 `2026-11-23-auth-mysql-account-login.md`와 공통 이메일 인증 계획: 기존 결정은 개인정보를 현재 ERD 컬럼 형식으로 저장하고 비밀번호는 15~128 Unicode 코드 포인트이며 문자 종류를 강제하지 않는다. 이는 공통 PRD의 이전 암호화·비밀번호 정책과 다르다. 이메일은 ASCII이며 전체 대소문자를 구분하지 않는다.
- 공통 백엔드 컨벤션의 계층·DTO·영속성·트랜잭션·오류·테스트 절을 따른다. 화면 및 프론트엔드 규칙은 범위 밖이다.

## 제안하는 동작과 선택

1. 입력과 중복을 확인하고 인증 증명의 이메일·목적·유효기간을 검증해 하나의 가입 절차에 연결한다.
2. 가입 진행 상태를 지속 저장하고 계정과 자격증명은 MySQL 트랜잭션으로 저장한다. ERD 기준 MySQL `user_profile`에 프로필을 저장하고 저장 완료 전에는 성공 응답 또는 로그인 가능 상태로 만들지 않는다.
3. Redis 증명과 MySQL 지속 기록은 단일 트랜잭션이 아니므로 Redis에서 증명을 삭제하지 않고 확인한 뒤 MySQL 트랜잭션에 사용 기록과 가입 결과를 저장한다. 단순 증명 삭제 후 DB 저장은 중간 장애에서 복구할 수 없어 사용하지 않는다. 동시 요청과 프로세스 종료도 고려한다.
4. 같은 키와 같은 입력은 기존 결과를 반환하거나 절차를 복구하고, 같은 키에 다른 입력은 충돌로 처리한다. 비밀번호·증명 원문을 로그나 영속 저장소에 남기지 않는다.

## 구현 전 검토할 사항

- 이번 가입은 ERD와 실제 MySQL `user_profile`을 기준으로 한다. MongoDB 프로필 저장 여부는 회원가입 구현 완료 후 검토한다.
- 사용자 결정: 약관 항목이 정해지기 전까지 가입 시 전체 동의한 것으로 처리하고 MySQL의 필수 동의값을 설정한다. 실제 항목·필수 여부·버전·동의 기록은 추후 결정한다.
- 사용자와 합의한 Redis 증명 확인·MySQL 원자 저장 및 24시간 재시도 기준을 아래 상세 설계에 반영한다.
- #3의 개인정보·비밀번호 정책과 공통 문서의 이전 정책 차이, 이메일 비교 기준과 DB 컬레이션 차이를 확인한다. 기존 사용자 결정을 바꾼 것으로 가정하지 않는다.
- 성별 코드, 상세 주소, 로그인 ID 비교 및 닉네임 제한을 제품 정책과 실제 DB 제약에 대조한다.

## 추가 요청: 가입 전 중복 확인 API

- 로그인 ID와 닉네임의 사용 가능 여부를 각각 조회하는 공개 API 두 개를 회원가입 범위에 추가한다. 경로·입력·응답은 아래 결정에 따르고 요청 제한은 별도 정책을 확인한다.
- 사전 확인은 값을 예약하지 않는다. 확인 후 동시 가입이 가능하므로 가입 저장 시 DB 유일 제약으로 다시 검증하고 중복을 충돌로 반환한다.
- 로그인 ID는 기존 MySQL `login_credential.login_id` 제약 및 실제 비교 규칙을 따른다. 닉네임은 MySQL `user_profile.nickname`의 유일 제약과 비교 규칙을 사용한다.
- 사용 가능·중복·잘못된 입력, 대소문자 등 비교 기준, 확인 직후 다른 요청이 선점하는 경합을 테스트한다. 실제 MySQL 유일 제약은 아래 읽기 전용 조사 결과를 따른다.

## 1단계 조사 결과 — 2026-11-24

- 설정된 실제 MySQL의 `information_schema`를 읽기 전용으로 조회했다. `login_credential.login_id`는 `VARCHAR(100) NOT NULL`, `uk_login_id` 단일 컬럼 UNIQUE다. `user_profile.nickname`은 `VARCHAR(50) NOT NULL`, `uk_profile_nickname` 단일 컬럼 UNIQUE다.
- 두 컬럼의 컬레이션은 `utf8mb4_0900_ai_ci`로 대소문자와 악센트를 구분하지 않는다. 정확한 입력 정규화·공백·문자 길이 규칙과 가입 API의 비교 방식은 별도 확정한다. 데이터 조회·변경은 하지 않았다.
- PRD ACC-01은 일반 회원 프로필의 MongoDB 저장을 확정했지만 실제 MySQL과 ERD에 닉네임 UNIQUE를 가진 `user_profile`이 존재한다. 사용자는 이번 구현에서 ERD 기준 MySQL을 우선하고 MongoDB 프로필 저장은 가입 구현 완료 후 검토하기로 했다. 실제 MongoDB 인덱스는 조사하지 않았다.
- PRD는 약관 내용을 MongoDB, 계정 동의 여부를 MySQL에 저장하도록 정하지만 약관별 필수 여부, 버전과 동의 기록 방식은 미정이다. 사용자 지시에 따라 이번 가입에서는 동의한 것으로 임시 처리하며 실제 약관·기록 정책은 나중에 정한다.
- 프로필은 이번 구현에서 ERD 기준 MySQL을 사용한다는 사용자 결정을 따른다. 약관은 이번 가입에서 동의 상태로 임시 처리하고 세부 정책은 추후 결정한다. 공통 문서 동기화는 가입 구현 후로 보류한다.


## 약관 임시 처리 결정 — 2026-11-24

- 사용자는 실제 약관과 필수 항목이 정해지지 않아 이번 가입에서 모두 동의한 것으로 처리하도록 지시했다. 가입 요청에 개별 약관 선택을 추가하지 않고 기존 MySQL 필수 동의 상태를 설정한다.
- 실제 약관 내용·필수 여부·버전·개별 동의 기록은 구현 이후 별도 결정한다. 이 임시 상태는 실제 약관을 보여주고 동의를 받은 증거가 아니다.


## 중복 확인 API 경로 결정

- `GET /api/auth/login-ids/availability?loginId=...`: 로그인 아이디 사용 가능 여부.
- `GET /api/auth/nicknames/availability?nickname=...`: 닉네임 사용 가능 여부.
- 성공 응답은 공통 형식의 `{"data":{"available":true}}`이며 사용 중이면 `false`다. 유효하지 않은 입력은 검증 오류로 처리한다. 조회는 예약이 아니므로 가입 시 유일 제약을 다시 검사한다.

## 일반 가입의 증명·멱등성 상세 설계 — 2026-11-24

### 사용자 결정과 대상

- #7 및 `feat/7-signup-api`에서 회원가입을 진행한다. 사용자는 Redis 증명을 확인한 후 증명 사용 기록·멱등 결과·MySQL 계정/자격증명/프로필을 하나의 트랜잭션으로 저장하고, 성공한 요청을 24시간 재시도하는 방식을 승인했다. Redis 만료/유실로 미완료 증명을 확인할 수 없으면 재인증한다. 프로필 MongoDB 이전 여부는 완료 후 재검토한다. 공통 문서는 이번에 수정하지 않는다.
- ERD `svc_identity.account`: uuid/email 각각 UNIQUE, status·name·phone_number·gender·birth_date·address·email·terms_agreed 필수. `login_credential`: account FK, account_id/login_id 각각 UNIQUE. `user_profile`: account FK, account_id/nickname 각각 UNIQUE, nickname/user_type 필수. 계정 생성 서비스는 기존 Argon2id·15~128 코드포인트 비밀번호 정책을 사용한다. 가입은 세 테이블을 한 트랜잭션으로 저장한다.
- `RedisVerificationStore.CONFIRM`은 증명 원문 대신 `HMAC(codeKey, 'proof:' + token)`을 키로, 이메일 HMAC·SIGNUP·만료 시각을 600초 저장한다. 검증은 원문을 로그에 남기지 않고 키/이메일 HMAC·목적·만료를 확인한다. Redis와 MySQL을 한 트랜잭션으로 취급하지 않는다.

### 제안하는 저장 모델과 동작

- 신규 MySQL InnoDB `signup_idempotency` 테이블을 명시적 마이그레이션으로 추가한다. 구현 후보 컬럼: `id BIGINT` PK, `key_digest BINARY(32) NOT NULL UNIQUE`, `proof_digest BINARY(32) NOT NULL UNIQUE`, `request_digest BINARY(32) NOT NULL`, `member_uuid CHAR(36) NOT NULL`, `completed_at DATETIME(6) NOT NULL`, `expires_at DATETIME(6) NOT NULL`, 삭제 작업용 `INDEX(expires_at)`. 증명·멱등 키·요청·비밀번호 원문은 저장하지 않는다. 구체 FK·배포 스크립트는 서비스 실제 DB 운영 방식과 함께 확인한다. 공유 DB에는 임의 적용하지 않는다.
- 클라이언트는 요청마다 충분한 난수의 고유 `Idempotency-Key`와 원래 인증 증명을 사용한다. 키·증명·비밀번호 등 포함한 요청의 정규화 기준과 필드 순서를 버전이 있는 길이 구분 인코딩으로 고정한다. 재시도에 필요한 동일 입력에는 증명과 비밀번호도 포함한다. 별도 고강도 비밀키를 사용한 HMAC으로 키와 요청 지문을 분리 생성하고 도메인을 구분한다. 일반 SHA 해시로 비밀번호를 보관하지 않는다. 상수 시간 지문 비교와 로그·예외 민감값 비노출을 적용한다. 키 유실/변경 시 기존 재시도 불가 및 키 회전 정책을 운영 절차에 적는다.
- 먼저 키 digest로 완료 기록을 조회한다. 24시간 내 기존 기록이면 Redis에 접근하지 않고 제출 증명을 포함한 요청 지문을 검증해 일치 시 최초 201·Location·memberId를 반환한다. 불일치는 409 IDEMPOTENCY_CONFLICT. 키만으로 가입 결과를 노출하지 않는다.
- 신규 요청은 Redis에서 증명·이메일·SIGNUP·만료를 확인한다. MySQL 트랜잭션의 쓰기 직전에도 검증된 만료 시각을 확인해 만료 후 새 사용을 시작하지 않는다. 이후 유니크 키/증명 digest 기록, 계정·자격증명·프로필·성공 결과를 동일 트랜잭션으로 커밋한다. 삽입 시각은 DB UTC 기준으로 저장하고 성공 결과 24시간 보장과 만료 경계·트랜잭션 장기 지연을 테스트한다. 정리 작업은 이 기한과 기존 증명의 만료 이후만 삭제하며 동시 재시도·트랜잭션과 경합하지 않아야 한다.
- 동일 키 경쟁 및 동일 증명의 서로 다른 키 경쟁은 MySQL UNIQUE가 직렬화한다. 유일성 예외가 발생한 트랜잭션은 롤백하고 별도 새 트랜잭션에서 커밋된 기록을 재조회해 동일 요청 재응답, 키 충돌, 사용된 증명 또는 계정 중복을 구분한다. 원인 미상의 DB 오류를 중복이나 성공으로 단정하지 않는다. 완료 기록이 없는 롤백 후 Redis 증명이 유효하면 같은 요청 재시도가 가능하다.
- Redis 검증과 MySQL 커밋 사이에 프로세스가 중단되어도 증명을 먼저 삭제하지 않으므로 유효한 경우 재시도할 수 있다. DB 저장 전 Redis 만료·유실은 재인증이 필요하다. DB 커밋 후 응답이 유실되거나 Redis가 유실되어도 완료 기록으로 같은 요청에 응답한다. 커밋 결과 불명확 또는 DB/Redis 장애는 실패/일시 오류로 처리하며 같은 키로 안전하게 재시도한다.
- 가입 정보의 이메일은 기존 정책대로 ASCII·양쪽 공백 제거·전체 대소문자 비구분 검증을 따른다. 아이디·닉네임은 기존 중복 API와 실제 DB 컬레이션 기준으로 저장 시에도 UNIQUE를 적용한다. 인증 증명과 관련 없는 단순 유효성 실패는 사용 처리하지 않는다. 약관은 사용자 지시에 따라 true로 임시 저장한다.

### 검증 및 남은 결정

- 단위·웹 계약 검증과 `./gradlew.bat test bootJar`; 격리 MySQL·Redis의 실제 인덱스, 트랜잭션 롤백, 동시에 같은 키/증명 경쟁, DB 커밋 후 응답 유실 및 Redis 장애, 증명 만료 직전/직후, 키 24시간 경계, 정리 작업 경합, 민감 로그 비노출을 검증한다. 실제 공유 DB 쓰기 금지. 서버 검증과 격리 DB 검증을 별도 보고한다.
- 사용자 결정: 성별 코드는 `MALE`·`FEMALE`, 계정 상태 코드는 `ACTIVE`·`SUSPENDED`·`WITHDRAWN`, 신규 가입 계정은 `ACTIVE`, `user_profile.user_type`은 `USER`다. 주소/상세 주소 표현은 별도 확인한다. 개인정보·비밀번호의 #3 사용자 결정은 유지한다.
- 증명/계정 조회·로그인 연계, 원격 MySQL 스키마 적용·배포, 키 주입·회전, 가입 후 공통 PRD·API·ERD 동기화는 구현과 운영 검토에서 확인한다. 커밋·푸시·PR은 별도 요청 범위다.

- 회원가입 API 구현과 스키마 스크립트가 작업 중이다. 검증·리뷰 결과가 확정되기 전이며 실제 공유 DB 스키마에는 적용하지 않았다.
